# 自动化探测中识别WAF/CDN拦截的通用方法：基于响应特征与工具调用统计的伪命中过滤

- 来源：任务 #36 自动复盘（自我迭代）
- 保存时间：2026-11-19 15:52

**结论先行**：本次任务中http_fetch调用105次但无任何发现，典型原因是所有请求均被WAF/CDN拦截或返回了无意义的默认页面（如“Welcome to nginx”）。通过分析响应状态码、内容长度、关键字和工具调用统计，可快速识别伪命中，避免浪费后续资源。

**适用场景**：任何自动化渗透测试中，当工具报告大量“存活站点”或“有趣目标”但实际无漏洞产出时，用于过滤无效资产。

**具体做法**：
1. **响应状态码过滤**：若所有存活站点返回200但内容相同（如统一登录页、CDN默认页），则可能被CDN缓存或WAF统一响应。应检查响应头中的Server字段（如“cloudflare”、“AkamaiGHost”）或Set-Cookie中的安全标记。
2. **内容长度与关键字**：对http_fetch返回的页面进行聚类，若大量页面长度接近且包含“403 Forbidden”、“Request Blocked”、“Please enable JavaScript”等关键字，则判定为拦截。可编写脚本自动计算页面哈希并去重。
3. **工具调用统计异常**：当httpx_probe调用次数少（如3次）但http_fetch次数多（如105次），说明存活探测阶段已发现大量目标，但后续深入请求均无有效响应。此时应检查httpx_probe的存活判定逻辑（是否仅基于状态码而非内容），并回看原始响应。
4. **被动验证**：使用curl或wget手动测试几个高价值子域名，带上真实浏览器User-Agent和Cookie，观察是否返回正常页面。若手动访问正常而工具失败，则说明工具请求被WAF识别。
5. **记录拦截指纹**：将常见的WAF拦截页面特征（如“Cloudflare Ray ID”、“Akamai Edge”等）存入知识库，后续任务自动跳过此类响应。

**注意事项**：
- 部分WAF会随机返回不同状态码（如200+假页面），需结合内容分析。
- 不要仅依赖状态码200判断存活，需检查页面标题或关键元素（如“login”）。
- 若发现大量伪命中，应优先调整工具配置（如添加Cookie、Referer、降低频率）而非继续深入。
